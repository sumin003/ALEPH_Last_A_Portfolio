# 우수민 포트폴리오

실패를 돌아보고 공부 방법을 바꾸며 배움을 이어 온 과정과, 직접 만든 프로젝트를 소개하는 공개 포트폴리오입니다. 처음 방문한 사람이 자기소개 이야기를 약 3분 안에 읽고, 기록과 결과물을 통해 함께 일할 이유를 확인할 수 있도록 구성했습니다.

- 사이트: https://alephlastaportfolio.vercel.app/
- 저장소: https://github.com/sumin003/ALEPH_Last_A_Portfolio
- 공개 연락 수단: sumin0516a@naver.com

HTML, CSS, JavaScript로 만들었으며 GitHub의 main 브랜치와 연결된 Vercel에서 배포합니다. 공개 페이지와 기록 갱신 기능은 회원가입이나 로그인 없이 이용할 수 있습니다.

## 자기소개 이야기

정보처리기사 실기시험 불합격에서 시작해, 감정을 받아들이고 공부법을 바꾸어 다시 시험을 치른 현재까지의 이야기를 담았습니다. 소설 원문은 사이트에 싣지 않고, 실제 경험을 바탕으로 자기소개를 정리했습니다.

세 능력은 다음 장면에서 드러납니다.

| 능력 | 이야기 속 장면 |
|---|---|
| 자기조절력 | 불합격의 실망을 받아들이고 자신을 탓하던 시선을 공부 방법으로 돌리는 장면, 진도가 느린 날에도 쉬고 다음 날을 준비하는 장면 |
| 대인관계력 | 동료들과 함께 공부하며 힘을 얻고, 주변을 챙기며 가족에게 필요한 도움을 행동으로 옮기는 장면 |
| 자기동기력 | 다음 시험 일정을 찾아보고 기출문제 중심으로 공부법을 바꾸어 재시험까지 이어 가는 장면 |

이야기는 첫 화면의 **이야기**에서 확인할 수 있습니다. 2026년 10월 20일의 공부 기록 장면을 본문에 표시했습니다. 숫자의 출처와 갱신 도구의 문단 후보에도 근거 날짜가 나옵니다.

## 숫자와 출처

기본 화면은 2026년 10월 30일까지 제공된 리추얼 기록을 기준으로 합니다.

| 항목 | 기본 수치 | 출처와 계산 기준 |
|---|---|---|
| 기록을 남긴 날 | 54일 | 리추얼 기록의 시작 또는 마무리에 내용이 있는 날짜를 중복 없이 계산 |
| 하루를 돌아본 날 | 47일 | 리추얼 기록 중 마무리에 내용이 있는 날짜만 계산 |
| 기록이 있는 달력주 | 12주 | 기록 날짜가 속한 월요일~일요일 기준 달력주를 중복 없이 계산 |
| T01~T11 과제 목록 | 11개 | 과제 목록의 항목 수이며 완료 건수나 제출률을 뜻하지 않음 |

리추얼 기록의 기간은 **2026-08-11~2026-10-30**입니다. 12주는 공식 교육 주차나 전체 13주 과정의 출석 주 수와 다릅니다. 기록이 없는 날을 임의로 채우지 않습니다.

공부 진도가 늦었던 2026년 10월 20일 이후에도 기록을 이어 갔다는 점은 10월 21일부터 30일까지의 기록 8일과 연결했습니다. 이는 기록을 지속한 근거이며, 시험 합격이나 능력 점수를 뜻하지 않습니다.

실제 출석 자료는 현재 기본 수치에 포함하지 않았습니다. 별도의 출석 파일을 넣었을 때에만 출석 수치를 표시합니다. 과제 목록도 전체 제출 현황으로 해석하지 않습니다.

## 소개와 프로젝트 경험

기존 포트폴리오의 공개 내용을 현재 사이트에 통합했습니다.

- 소개: 장점, 취미, 학습 분야, 전공·졸업 정보
- 통학버스 예매 시스템: 노선·시간 조회, 좌석 선택과 예매 화면, 설계·문서화·협업 경험
- PIND 브라우저 확장 프로그램: Plasmo를 활용한 YouTube와 PIND 웹앱 연결 경험
- 테이블톡: 식당 조회, 예약, 예약 내역 관리 화면과 기능 구현 경험
- 목표: 프론트엔드를 시작으로 다양한 분야를 배우며 개발 역량을 넓혀 가는 방향

첫 화면의 **나를 소개합니다.** 또는 **직접 만든 프로젝트**에서 이동할 수 있습니다. 각 프로젝트의 **과정과 근거 보기**를 펼치면 상황·행동·결과와 기능 흐름도 또는 GitHub 링크가 나옵니다. 패스키 인증과 비공개 영역은 포함하지 않았습니다.

## 대표작

**대표작**에는 T10 논문과 T13 앱의 예정 자리가 있습니다.

- 논문: 「공개 장애 보고서 비교를 통한 네트워크와 서버 장애 대응의 개선 방안」
- 논문 파일: `documents/research-paper.docx`
- 앱: T13을 마친 뒤 기능, 제작 과정, 실행 링크를 추가할 예정이며 공개일은 미정

논문은 로그인이 필요한 외부 문서 링크 대신 사이트에서 직접 내려받는 DOCX로 제공합니다. 다른 개인 저자명을 생략한 공개용 사본입니다. 연구 내용은 공개 문헌과 사례 비교에 근거한 개선 제안이며, 실제 도입 효과를 입증했다는 의미는 아닙니다.

## 새 기록으로 갱신하기

1. 사이트의 **기록 갱신**에서 리추얼·기록 JSON 또는 UTF-8 TXT 파일을 선택합니다. 실제 출석 자료가 있으면 출석 JSON 파일도 선택할 수 있습니다. 과제 목록은 T01~T11 기본 목록을 사용하므로 별도로 업로드하지 않습니다.
2. 다시 계산된 숫자와 능력별 문단 후보를 확인합니다. 후보에는 기록 날짜와 근거 필드가 표시됩니다.
3. 실제 경험과 공개 여부를 확인한 문장만 선택하고 **선택한 문장 반영**을 누릅니다. 선택한 문장은 이야기 아래에 추가됩니다.

파일은 브라우저에서 처리합니다. 숫자는 파일을 읽은 직후 바뀌고, 문장은 선택·승인한 뒤에만 추가됩니다. 현재 결과는 해당 브라우저의 localStorage에 저장됩니다. 다른 브라우저나 다른 방문자의 공개 화면을 바꾸는 서버 저장 기능은 없습니다.

문단 후보는 본인이 쓴 경험·회고에서 관련 낱말을 찾아 발췌하는 방식입니다. AI API를 호출하지 않으며 원문에 없는 사건을 생성하지 않습니다. 후보의 능력 분류와 사실 여부는 사용자가 최종 확인합니다.

같은 기록·과제·출석 파일을 넣으면 같은 숫자와 후보를 만듭니다. 승인 여부는 사용자의 선택에 따라 달라집니다. 잘못된 형식이나 날짜가 있는 파일은 오류를 안내하고 기존 집계와 이야기를 유지합니다. 파일 크기 제한은 파일당 5MB입니다.

## 입력 파일 형식

### 리추얼 JSON

기존 리추얼 내보내기 파일의 `days` 배열을 읽습니다. `open`과 `close`는 문자열 배열 또는 기록 유무를 나타내는 불리언입니다.

```json
{
  "days": [
    {
      "date": "2026-10-30",
      "open": ["강점을 위해 노력하고 생각한 것: 오늘의 공부 순서를 정했습니다."],
      "close": ["나에게 남기는 말: 계획을 돌아보고 내일 다시 공부하겠습니다."]
    }
  ]
}
```

### 일반 기록 JSON

```json
{
  "records": [
    {
      "date": "2026-10-30",
      "ability": "자기동기력",
      "text": "공부 방법을 바꾸어 다시 시도했습니다."
    }
  ]
}
```

능력은 `자기조절력`, `대인관계력`, `자기동기력` 중 하나입니다. 같은 날짜가 여러 번 나와도 기록일은 하루로 계산합니다.

### TXT

날짜를 줄 첫머리에 쓰고 아래에 내용을 적습니다. `YYYY-MM-DD`, `YYYY.MM.DD`, `YYYY년 M월 D일`을 지원합니다. 마무리 기록은 `마무리:` 또는 `회고:`로 구분합니다.

```text
2026-10-30
공부 방법을 바꾸어 다시 시도했습니다.

2026-10-31
마무리: 동료와 함께 공부하며 도움을 나누었습니다.
```

날짜가 없는 파일은 집계하지 않습니다. 위 JSON·TXT 내용은 입력 형식을 설명하는 예시이며 실제 기록 수치에 포함되지 않습니다.

### 기본 과제 목록과 선택 출석 자료

- 기본 과제 목록은 `data/tasks.json`에서 관리합니다. 기록 업로드 시 이 목록을 자동으로 사용합니다.
- 과제 ID 범위: 중복 없는 T01~T11
- 상태: `completed`, `in_progress`, `planned`; 그 외에는 확인되지 않은 상태로 처리
- 출석: `{"as_of":"2026-10-30","attended_days":9,"scheduled_days":13}`

출석 예시의 숫자는 형식 설명용입니다. 실제 출석 자료의 값만 입력하며, 출석일은 대상 수업일보다 클 수 없습니다.

## 소스 구성과 실행

```text
index.html               공개 화면과 기본 집계 데이터

script.js                파일 입력, 문장 승인, 브라우저 저장
record-engine.js         브라우저와 실행 장치가 함께 쓰는 집계 코드
tools/refresh.cjs        집계 생성, 사용자 승인, 공개용 사이트 생성

input/                  익명화 기본 기록과 승인 목록

```

## 장치 실행 방법

Node.js 18 이상에서 추가 패키지 설치나 API 키 없이 실행합니다. Windows의 터미널에서도 같은 명령어를 사용할 수 있습니다. ZIP을 새 폴더에 풀고 그 폴더에서 아래 세 단계를 진행합니다.

1. **기록을 넣고 결과를 만듭니다.** 새 리추얼 파일을 `input/ritual.json`으로 저장하거나 `--input`에 JSON·TXT 경로를 지정합니다.

```bash
node tools/refresh.cjs generate --input input/ritual.json --output output
```

2. **후보를 확인하고 직접 승인합니다.** `output/candidates.json`에서 문장·날짜·근거와 `id`를 확인합니다. 공개할 후보의 실제 ID를 아래 명령에 넣습니다. 승인할 것이 없으면 이 단계는 건너뜁니다.

```bash
node tools/refresh.cjs approve --input input/ritual.json --id 선택한후보ID
```

여러 문장은 `--id`를 반복합니다. 승인 명령은 승인 목록 전체를 교체합니다. `--id` 없이 `approve`를 실행하면 승인을 취소합니다. 후보의 내용이 바뀌면 기존 승인은 거절되며 다시 확인해야 합니다.

3. **사이트 파일을 만듭니다.**

```bash
node tools/refresh.cjs build --input input/ritual.json --output output --site site
```

`site/index.html`과 문서·이미지·스크립트가 생성됩니다. 이 폴더의 내용을 정적 서버로 열어 확인하고 GitHub에 반영하면 다른 방문자에게도 공개할 수 있습니다. 입력 원문과 미승인 후보는 공개용 `site/`에 포함하지 않습니다. 이미 승인한 문장은 `site/index.html`과 `site/data/site-data.json`에 들어갑니다. 명령 실행만으로 GitHub 업로드·Vercel 배포를 자동 수행하지는 않습니다.

실제 출석 자료는 생성·승인·빌드 명령에 동일하게 `--attendance 파일경로`를 추가하면 됩니다. 기본 과제 목록은 T01~T11이며 별도 과제 업로드는 없습니다.

동봉한 `input/ritual.json`은 기존 리추얼에서 날짜별 기록 유무와 능력 분류만 남긴 공개용 입력입니다. 이 입력의 후보는 구체적인 원문 경험을 재현하는 문장이 아니므로 사용자가 적합성을 확인해야 합니다. 원문은 동봉하지 않습니다. 마지막 결과는 승인 0건이며 시험용 승인을 실제 사용자 승인으로 표시하지 않습니다.

## 같은 입력 두 번 실행 확인

```bash
node tools/verify.cjs
```

새 임시 폴더에 필요한 파일을 복사하여 같은 입력으로 두 번 빌드하고, `output/`과 `site/`의 파일별 SHA-256을 비교합니다. 날짜 검증, TXT 중복 제거, 미승인 문장 제외, 명시적 승인·취소, 변경된 후보 승인 거절도 확인합니다. 승인을 시험하는 과정은 임시 폴더에서만 실행합니다. 결과는 `verification/comparison.json`에 저장됩니다.

웹페이지는 별도 패키지 설치 없이 실행할 수 있습니다. 로컬 정적 서버가 필요하면 Python 3가 설치된 환경에서 아래 명령을 실행한 뒤 `http://localhost:8000`으로 접속합니다.

```bash
python -m http.server 8000
```

브라우저 입력과 명령행 장치는 같은 `record-engine.js`를 사용합니다. 기본 화면은 `index.html`에 포함된 데이터를 읽습니다. `data/site-data.json`만 수정해도 기본 화면이 자동으로 바뀌는 구조는 아닙니다.

- **지원 문서:** 지원문서 메뉴에서 DOCX 3개 다운로드
- **갱신 기능:** 기록으로 사이트 갱신하기에서 동일한 파일을 두 번 선택해 숫자와 후보의 내용·순서 비교
- **새 폴더 실행:** 소스를 새 폴더에 풀고 위 실행 방법으로 접속해 파일 입력과 문장 반영 확인

장치 ZIP에는 실행 소스, README, 익명화 입력, 마지막 결과와 `site/` 공개용 결과를 함께 담았습니다. 지원 문서 3개와 장치 ZIP은 사이트의 다운로드 버튼 여부와 별개로 파일 제출이 필요합니다. 마지막 결과를 함께 제출할 때는 실제 승인 결과를 담고, 입력 예시를 실제 기록으로 바꾸어 적지 않습니다.

공개 화면과 제출 파일에는 본인 이름과 정한 연락 수단 외에 다른 사람의 실명·연락처, 비밀번호·토큰·API 키가 포함되지 않도록 확인합니다. 자동 연락처 가림만으로 모든 이름과 비밀값이 제거되는 것은 아니므로 승인 전 원문을 직접 살펴야 합니다. 제출 URL과 문서 다운로드는 새 시크릿 창에서도 확인합니다.

## AI와 나의 판단

- **AI에게 맡긴 일:** 사이트와 기록 갱신 기능의 코드 작성·수정, 기록 집계와 문단 후보 추출, 지원 문서 및 README 초안 정리.
- **직접 판단한 일:** 실제 경험과 자기소개 표현, 공개할 내용과 연락 수단, 사이트 구성과 디자인, 필요한 기능의 범위 결정.
- **AI 제안을 따르지 않은 일:** 인증을 요구하는 기록 관리 방식과 불필요한 날짜 안내·예시 다운로드·초기화 버튼을 제외하고, 로그인 없이 확인할 수 있는 구성으로 변경하도록 요청.

## 제출자가 직접 확인할 항목

- 이야기의 첫 문장과 마지막 문장을 본인의 표현으로 최종 확정합니다.
- 동료 한 사람에게 읽히고 같이 일하고 싶은 이유 한 가지를 듣습니다.
- T13 앱의 실제 공개 예정일을 정하면 사이트에 기입합니다. 현재는 미정입니다.
- 새 시크릿 창에서 사이트와 문서 다운로드를 확인하고, 제출 화면에 HTTPS 결과물 URL 한 개와 문서·장치 ZIP을 첨부합니다.

위 항목은 AI가 대신 수행했다고 표시하지 않습니다. 자동 실행 검사는 동료 피드백이나 실제 제출 확인을 대신하지 않습니다.
